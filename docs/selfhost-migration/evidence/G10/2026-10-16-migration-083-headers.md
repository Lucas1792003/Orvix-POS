## Finding (stopped here, reported to the owner)
**PNG completion inconsistency.** The bucket (083) and the function's byte check accept PNG, but `complete_product_image_upload_session` still allows only WebP/JPEG (since 075/079), so a valid PNG is refused at completion with "Unsupported uploaded image type" (422 `completion_refused`) and — unlike a byte-check refusal — the object is **not deleted** (stays at its `org/<org>/temp/<session>` path, session PENDING; the prepared sweep removes such objects after 24 h). Not a security issue (real image, served with the new headers); a functional mismatch with "JPEG, PNG and WebP". Both apps re-encode photos to WebP/JPEG, so no app produces PNG today. Options: (a) migration 085 adding `image/png` to the RPC's allowed types (function already validates PNG); (b) make the function refuse PNG up front and delete it (bucket then still allows PNG for staff direct writes until 084). Needs owner decision.

## Correction (2026-10-16, after the 085 work)
The finding above was partly wrong. Re-analysis (docs/selfhost-migration/phase-f/migration-085-png.md): the deployed 083-era function's byte check did **not** accept PNG — it refused it and deleted the object. The live G5-2 failure came from the test's own follow-up RPC call (`image/png` hits the RPC's type check before its "object missing" check). The real gap was different: when the **RPC** refused after a passing byte check (type, size, object missing, not configured), the object stayed at `org/<org>/temp/<session>`. Fixed by 085 (PNG accepted consistently) plus the scoped delete-on-refusal in `phone-upload-token`, deployed 2026-10-16 07:51–07:52 UTC (see G11).
