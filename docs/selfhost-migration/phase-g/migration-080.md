File: `supabase/migrations/080_upload_completion_trusted_url.sql`
(407 lines, sha256 `d8b38edd…b318f2`). It was generated by `gen080.py` in the

Closes `docs/lucashome-selfhost/risks.md` → "Upload completion checks the
path suffix, not the host".

## 1. The defect

079 required `p_public_url` to **end with**
`/storage/v1/object/public/product-images/<session path>`. It did not check
the host. Anyone holding a phone token could submit
`https://example.invalid/storage/v1/object/public/product-images/<session path>`.
That URL was then:

1. stored in `product_image_upload_sessions.public_url`,
2. returned by the desktop poll (`get_product_image_upload_session_status`),
3. passed by `ProductImagePhoneUploadModal` to `onUploaded(publicUrl)` and
   from there to `ProductImageInput`, and saved by the product form to
   `products.image_url` (`productSlice.ts`).

This was confirmed live on 2026-10-13. Completion also never checked that the
object had actually been uploaded.

## 2. Design

### 2a. Trusted base: decision

| Option | What it is | Verdict |
|---|---|---|
| (a1) `ALTER DATABASE postgres SET app.settings.storage_public_base = …` | A GUC read with `current_setting()` | **Rejected.** Any session can shadow it with `SET`. Setting a placeholder GUC per database needs elevated rights, which differ between hosted and self-host. It is invisible in dumps of `public`. It also cannot be shape-checked. |
| **(a2) `public.app_config(key, value)`, one row per setting, writable only by service_role, seeded per environment** | A table with CHECK constraints | **Chosen.** It is authoritative and auditable (`updated_at`), and it appears in logical backups. Its shape is enforced by a constraint. No API role except service_role can read or write it. The migration does not hard-code a host. |
| (b) Store only the path; each client builds `getPublicUrl(path)` from its own `VITE_SUPABASE_URL` | No server URL at all | **Not chosen.** It is safe for the desktop, because the desktop's backend URL is trusted and pinned by `VITE_SUPABASE_EXPECTED_HOST`. But it needs desktop changes in files another agent is editing right now. It also leaves `publicUrl` in the RPC responses either client-shaped or empty. Old Electron builds, which update on their own schedule, would keep storing whatever the poll returned. (a2) fixes every client build already deployed, without a client change. |

The trade-off of (a2) is **one operator step per environment**, because the
value is not seeded. The design **fails closed**:

- Until the base is set, completion raises `Phone image upload is not
  configured on this server`, and the session stays PENDING.
- Until the base is set, the readers return `publicUrl: null`.

The desktop modal only calls `onUploaded` when `publicUrl` is non-null, so a
wrong or caller-supplied URL can never be stored. Section 5 lists the
commands.

`app_config`:
- `key` must be `'supabase_public_url'` (CHECK `app_config_key_known`).
- `value` must be `https://<lower-case host>[:port]`, or
  `http://localhost|127.0.0.1[:port]` for local development. There can be no
  path, query, fragment, userinfo or trailing slash (CHECK
  `app_config_supabase_public_url_shape`).
- The value is the environment's **public API origin**. This is the same value
  as the web/desktop build's `VITE_SUPABASE_URL` and the stack's
  `SUPABASE_PUBLIC_URL`.
- Grants: `REVOKE ALL FROM PUBLIC, anon, authenticated, service_role`, then
  `GRANT SELECT, INSERT, UPDATE, DELETE TO service_role`. RLS is on with no
  policies. The owner is `postgres`, the same owner as the RPCs.

Helper `app_upload_session_public_url(path)`:
- Returns `base || '/storage/v1/object/public/product-images/' || path`.
- Only works for a path shaped like a session path,
  `^(org/[A-Za-z0-9_-]+/)?temp/[A-Za-z0-9_-]+$`. For anything else, or when
  the base is not set, it returns NULL.
- It is SECURITY INVOKER. EXECUTE is granted to service_role only. The
  SECURITY DEFINER RPCs call it as their owner, `postgres`.
- The bucket is hard-coded as `product-images`, the only bucket (016).

### 2b. `complete_product_image_upload_session`

The signature, return keys, SECURITY DEFINER, `search_path` and grants are all
unchanged, and anon keeps EXECUTE. The body is 079's, byte for byte, plus 4
edits. difflib shows them as 5 hunks, because the unchanged `RAISE … does not
match` / `END IF;` pair of the replaced 079 block stays as context. The
generator asserts every hunk; see the appendix.

1. **DECLARE:** adds `v_object_meta jsonb, v_public_url text, v_bytes integer, v_mime_type text`.
2. **`p_storage_path`: explicit rejection, then exact equality.** The value
   is refused with `Upload path does not match this session` when it:
   - is NULL or empty;
   - contains any character outside `[A-Za-z0-9/_.-]`. That excludes `?`, `#`,
     `%` (so every percent-encoding: `%2F`, `%2f`, `%2e%2e`), `\`,
     whitespace, control characters and any non-ASCII character (unicode
     lookalikes, fullwidth `／`, zero-width space, combining marks). The
     check is also spelled out as a second regex,
     `[?#%\\[:space:][:cntrl:]]`;
   - contains `..` or `//`;
   - starts or ends with `/`.

   The function also refuses if the **session's own** stored path is not
   session-shaped.

   After that comes the existing `p_storage_path IS DISTINCT FROM
   v_session.storage_path` check. **The comparison is exact byte equality.**
   The collation is deterministic (`en_US.UTF-8`, libc), and no
   `lower()`/`btrim()`/`normalize()` is applied anywhere, so an upper-case
   variant never matches. The value is only compared, never used.
3. **`p_public_url` is never stored and its host is never used.** It
   replaces 079's suffix test. For compatibility with deployed phone pages,
   which send `getPublicUrl(storagePath)`, the value must still be printable
   ASCII with no `?`, `#`, `%` or `\`. Its path, meaning everything after
   `scheme://authority`, must **equal** exactly
   `/storage/v1/object/public/product-images/` followed by the session path.
   Otherwise the call fails with `Uploaded image URL does not match this
   upload session`. The 019 checks (not empty, not `data:`, contains the
   bucket path) are unchanged and run first.

   **Decision: a foreign host is ignored, not rejected.** The value is
   discarded, so rejecting a host adds no security. It would, however, add an
   availability risk: a phone page built with a differently spelled but
   legitimate origin (port, alias, LAN name) would be refused. t16 asserts
   that the stored, returned and polled URL is always the trusted one, and
   that `evil.example` appears nowhere in the row.
4. **The object must exist.** The function looks for
   `storage.objects WHERE bucket_id = 'product-images' AND name =
   v_session.storage_path`. If there is no row, it raises `Uploaded image was
   not found in storage`. The RAISE rolls the call back, so the session stays
   PENDING and the phone can retry after the upload finishes.
5. **`bytes` and `mime_type` come from the object.** They are taken from
   storage-api's metadata (`metadata.size`, `metadata.mimetype`, written by
   storage-api v1.74 `uploader`/`file` backend) when present, and from the
   client values otherwise. They are then re-validated against ≤ 102400
   bytes and `image/webp|image/jpeg`. The bucket's own limit is 131072 bytes
   (016), so this check is stricter than the bucket.
6. **`public_url := app_upload_session_public_url(v_session.storage_path)`.**
   If it is NULL, the call raises `Phone image upload is not configured on
   this server`.
7. The UPDATE writes `storage_path`, `public_url`, `bytes` and `mime_type`
   from **server values only**.

**Repeated completion is rejected.** This is unchanged since 019/075. Any
second call raises `Upload link is no longer active` and leaves the row
byte-identical. No rows are ever inserted, so no duplicates are possible.
Reasons:
- Completion is a one-way state change.
- An idempotent "return the previous result" path would hand completion data
  to anon callers for sessions that are already finished.
- It would change a line that 075/079 tests rely on.

The client already handles a lost response. The JIT flow that is being built
re-reads the session and treats `COMPLETED` with the same `storagePath` as
success (see section 4).

**Expired and cancelled sessions are rejected** with the same message, `Upload
link is no longer active`, whether or not the object exists. This is
unchanged since 075/079.

### 2c. Readers

`get_product_image_upload_session_status` (the desktop poll) and
`_by_token` (the phone) each have one hunk. `'publicUrl'` is now:
- the derived URL when `status = 'COMPLETED'`;
- null otherwise;
- **never the stored column.**

So a pre-080 row that holds a caller-supplied URL (such as the live
`example.invalid` test row) is not returned to a desktop again. Both
functions keep the same keys (t15's 8-key check passes) and the same grants.

### 2d. Pre-conditions (checked inside the migration)

A DO block at the end aborts the whole transaction unless all of these hold:
- `storage.objects` exists.
- `complete_…` is owned by `postgres`. This is true in the snapshot, and
  `CREATE OR REPLACE` keeps the owner.
- `postgres` can SELECT `storage.objects`. storage-api tenant migration 0049
  runs `grant all on storage.buckets, storage.objects to postgres`.
- `postgres` is not subject to RLS on it. The supabase/postgres image gives
  `postgres` `BYPASSRLS`, as the harness shows.
- `app_config` and the helper are owned by `postgres`. The migration runs
  `ALTER … OWNER TO postgres`, because lucashome applies migrations as
  `supabase_admin`.

When the base is not set yet, the block emits a NOTICE.

I simulated the lucashome apply path in the harness container: 080 run as
`supabase_admin` with `--single-transaction`, twice. Results:
- It applied cleanly both times.
- Owners: `app_config`, the helper and the three RPCs are all owned by
  `postgres`.
- ACLs: `app_config` `{postgres=arwdDxtm, service_role=arwd}`, helper
  `{postgres=X, service_role=X}`.
- The anon-executable set is still exactly `app_setup_needed`,
  `complete_product_image_upload_session` and
  `get_product_image_upload_session_by_token`.

A negative test (`ALTER ROLE postgres NOBYPASSRLS` inside a transaction, then
080) aborted with `080: postgres is subject to RLS on storage.objects (needs
BYPASSRLS)`. The transaction was rolled back.

## 3. Client impact

**No client change is required for correctness**, and no client file was
edited. The files being edited concurrently were not touched.

- **Desktop** (`ProductImagePhoneUploadModal.tsx`): it polls
  `get_product_image_upload_session_status` and calls
  `onUploaded(result.publicUrl)` when the status is COMPLETED and the URL is
  non-null. After 080 that URL is always `<base>/storage/v1/object/public/product-images/<session path>`.
  The `products.image_url` written by the product form is therefore the
  trusted URL. t16 checks this by writing the polled value into
  `products.image_url` and asserting that it names an existing object.
- **Phone** (`PhoneProductImageUploadPage.tsx`, both the current build and
  the JIT rewrite): it sends `getPublicUrl(storagePath)`, which passes check
  2b-3 whatever origin the page was built for. It displays
  `completed.publicUrl` only as a status. The new error messages surface
  through `error.message`, as before.
- **Recommended clean-ups.** These are optional, for the agent that owns those
  files, and none of them is needed for security:
  1. `src/lib/productImagePhoneUpload.ts` `completeProductImageUploadSession`:
     keep sending `p_public_url: getPublicUrl(storagePath)`. The RPC
     signature is unchanged, so do **not** drop the argument. Comment that the
     server ignores its host and derives the stored URL.
  2. Map the new messages to friendly copy on the phone:
     - `Uploaded image was not found in storage`: "The photo did not finish
       uploading. Try again." The session stays PENDING, so a retry with a
       fresh token works.
     - `Phone image upload is not configured on this server`: "Phone upload
       is unavailable. Ask the admin." (operator action, section 5).
  3. Desktop: no change. Optionally, refuse a `publicUrl` whose origin differs
     from `VITE_SUPABASE_URL` as a belt-and-braces check. It can only differ
     if `app_config` is misconfigured.

### Compatibility with the JIT phone flow being built concurrently

This is based on the working tree, read only: `supabase/functions/phone-upload-token/index.ts`
and the in-progress `productImagePhoneUpload.ts`.

- The Edge Function signs **exactly** `session.storage_path` in
  `product-images` with `upsert:false`, after it checks that path against the
  expected `org/<org>/temp/<id>`. The phone's `uploadToSignedUrl` therefore
  creates the very object that 080 requires. ✔
- The Edge Function reads the session through
  `get_product_image_upload_session_by_token` to stamp expiry. Only that
  function's `publicUrl` value changes, and only for COMPLETED sessions. ✔
- `uploadPhoneProductImage` calls `complete` with
  `publicUrl(storagePath)`. On an error, it re-reads the session and returns
  success when it is `COMPLETED` with the same `storagePath`. That is the
  correct handling for 080's "repeated completion → rejected" rule, and for a
  lost response. ✔
- If the Edge Function ever signs a different bucket or name, or the phone
  uploads somewhere else, completion now fails with `Uploaded image was not
  found in storage` instead of silently attaching a URL. That is intended.
- 080 does not depend on the Edge Function, and the reverse is also true.
  Either can ship first.
