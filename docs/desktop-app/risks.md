# Desktop app — risks

- **Client/server coupling.** v1.0.15 sends no idempotency key → every mutating call fails against lucashome (062+). The branch client needs migration 076 for `/setup`. Order: server migrations first, then the new build.
- **Unsigned installers.** Windows SmartScreen warnings on manual install; macOS ad-hoc signature (Squirrel.Mac auto-update expected not to work). Decision: buy signing certificates or accept.
- **Version not bumped** — still 1.0.15 on the branch; must be 1.0.16 before publishing, or tills will not see it as an update.
- **Canary mechanism unproven** — `electron-updater` ignoring GitHub pre-releases is assumed, not tested.
- **`npm run build` (web) still uses `.env.local` → hosted**; only `build:electron` is host-pinned. The Vercel web build (Hobby plan) still points at hosted; usage unknown.
- **Whole-repo lint** reports 24 pre-existing errors in `src/lib/zawgyi.ts` (untouched).
- **E2E duplicate-sale heuristic** can flag two legitimate sales < 2 s apart (seen once 2026-10-12); left strict on purpose.

## Found 2026-10-16 — RC1 (b777345) owner-override audit; RC1 NOT changed, owner decides on an RC2
Evidence: characterization tests `audit/rc1/*.audit.test.ts` (8 passing; they pin RC1 as it is). PASS: export format v1 stable (3c00aeb files and a frozen RC1 file decrypt and dry-run replay); the Dexie v1→v2 upgrade and startup quarantine keep every 1.0.15 row and payload (pending/syncing/failed/conflict); export is read-only; override/update/quarantine/startup/logout never delete or mark rows synced; a sale queued after the export revokes the override; same appId/userData, NSIS keeps app data.
- **D1 (medium) Dismiss is one click, no confirmation, hard delete** — `src/pages/SyncConflictsPage.tsx:130-145,217-223` → `dismissOutboxEntry` (`src/stores/data/outbox.ts:546`). Export-first applies to quarantined rows only (session-scoped `wasExported`); a pending/conflict sale is deleted without any export. After a dismiss the list re-renders and the next row's Dismiss moves under the pointer, so a double click can remove two entries (code reading, not run). The toast "Its local record is kept" is false for 1.0.15 leftovers: the origin change cleared the local `sales` snapshot (`backendOrigin.ts:126-133`). Proposed fix: confirmation dialog naming the entry; export-first for every status; permission check in `dismissOutboxEntry`; keep focus/disable list during refresh.
- **D2 (medium) a row left `syncing` is never drained again** — `outbox.ts:455` sets `syncing`; the drain picks only `pending|failed` (`outbox.ts:36,383`); nothing resets it at startup. A quit mid-request (crash, power loss, or the recovery install during a drain) leaves it stuck: kept and exported, but it blocks every normal update (`countUnsyncedOutbox`) until a manual Retry. Pre-existing since 1.0.15. Proposed fix: at startup (single instance, drain lock held) reset `syncing` → `pending` (idempotency key makes the resend safe).
- **D3 (medium) provisional-id map pruned under quarantined entries** — `pruneProvisionalIdMap` (`outbox.ts:104-113`) deletes mappings > 7 days on every drain pass, also those a quarantined (never-draining) entry references; a later export lacks them and the replay reports `blocked-unresolved-ref` (manual reconstruction needed). Proposed fix: skip mappings referenced by any remaining outbox entry's `refs`.
- **D4 (low) "Owner only" override is text only** — `evaluateInstallGuard(…, {recovery:true})` (`electron/updateGuard.cjs:81-88`) does not need a signed-in owner; any user can export with their own passphrase and press "Install anyway (after export)" (`src/components/layout/CheckForUpdatesButton.tsx:187`). Rows stay on the till, so no data loss; the risk is a file whose passphrase only a cashier knows. Proposed fix: show/allow the button only for ADMIN (renderer) and report `role` in the app state.
- **Note** — 1.0.15 entries get an idempotency key minted by the 1.0.16 Dexie upgrade (`localDb.ts:216-227`); hosted never saw it, so a replay of a 1.0.15 entry cannot be de-duplicated by the server — check migrated data before replaying (register rule, `till-readiness-084.md` §2.1).
- **Canary plan correction** — a hand-started installer bypasses the updater guard; the old line 6.1 ("1.0.16-test-update installer stays Waiting") could not pass and would leave a test build on a shop till. Removed from the shop canary (`canary-1.0.16-checklist.md` §6).
